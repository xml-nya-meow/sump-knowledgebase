## 1. 先确定你手里是哪一版

代码会变化。教程今天说 `shell` 不排队，不代表半年前也如此；看到旧截图与新程序不同，也不一定是操作错了。

本组课程固定对应 [这一次源码提交](https://github.com/NouSart/sump/tree/6325897cc7fa696610bc25b4c89bc77d6a7c7a43)。可以从这个链接在线阅读，也可以下载 [固定提交 ZIP](https://github.com/NouSart/sump/archive/6325897cc7fa696610bc25b4c89bc77d6a7c7a43.zip)。

下载后解压到自己选择的学习目录。打开后应能看到 `go.work`、`protocol`、`service`、`reasoner`、`frontend` 等；如果只看到另一个同名文件夹，再进入一层。

**ZIP 快照**只有文件内容。**Git 克隆**还带版本历史和分支管理能力。学习源码可以先用 ZIP；要提交修改则通常需要 Git 工作副本。不要把解压新版本覆盖到存有个人改动的旧文件夹。

## 2. 每读一个模块，按同一套顺序找

不必从第一行读到最后一行。先回答几个有具体落点的问题。

| 你想知道什么 | 优先找哪里 | 读到什么才算找到 |
| --- | --- | --- |
| 程序如何启动 | `main.go` 或服务入口文件 | 启动参数、构造服务、Start、退出处理 |
| 这个模块依赖什么 | `go.mod`、`package.json`、`pyproject.toml` | 自有模块、第三方库、运行环境 |
| 它声明能做什么 | `Provides` / 动作名片 | action、tool、async、batchable |
| 收到动作后谁处理 | `Handle` 与处理函数 | 参数解码、校验、业务路径、返回值 |
| 保存的数据是什么 | `store` 等存储目录 | 表结构、读写方法、数据归属 |
| 它调用了谁 | `Call`、`Fire`、`jumpTo` 等调用点 | 服务名、动作、输入、trace/boss |
| 怎样得知结果 | response / report_result / 事件处理 | 配对编号、终态、错误路径 |
| 作者想保证哪些行为 | `*_test.go` 等测试文件 | 输入、断言、异常场景与清理 |

**断言**是测试中的“实际结果必须符合这个条件”。测试函数存在，只代表写下了检查程序；只有实际运行且结果通过，才能说它在该环境通过。

## 3. 用 timer 拆开一个完整服务

timer 逻辑相对集中，适合第一次读。先不用理解 MCP、模型 API 或数据库。

### 第一步：main.go 是启动说明

打开 [timer/main.go](https://github.com/NouSart/sump/blob/6325897cc7fa696610bc25b4c89bc77d6a7c7a43/timer/main.go)。里面通过 `flag` 读取参数，例如服务名字、监听地址、中心地址、最大计时时长、最大计时数量。

**参数 flag** 是启动程序时给它的选项；**默认值**是在你没有提供选项时使用的值。

然后它调用 `server.New(...)` 创建实例，再调用 `Start(...)`。程序等退出信号，退出时停止计时并关闭服务。`New` 和 `Start` 分开，是为了先把动作、配置、内部状态准备好，再真正接收外部请求。

### 第二步：go.mod 是依赖说明

打开 [timer/go.mod](https://github.com/NouSart/sump/blob/6325897cc7fa696610bc25b4c89bc77d6a7c7a43/timer/go.mod)。

- `module` 是这个 Go Module 的导入身份。
- `require` 列出依赖。
- `replace ... => ../protocol` 表示开发时去相邻目录使用这份协议代码。
- `go.work` 则把整个多模块工作区放在一起开发。

仓库迁到新组织后，源码中的 Go module 路径仍可能是旧仓库名字。这是当前源码约定，不是让读者手动全局替换的指示。

### 第三步：New 把业务接到骨架上

打开 [timer/server/server.go](https://github.com/NouSart/sump/blob/6325897cc7fa696610bc25b4c89bc77d6a7c7a43/timer/server/server.go)。`Server` 组合了一份 `*service.Service`，另有自己的 `pending` 计时表和锁。

**组合**就是把现成对象放进自己的对象里使用。公共骨架处理联网，timer 自己处理“还剩多少计时器、什么时候触发”。

下面摘取 `sleep` 名片中的关键字段，省略描述部分，**不是可单独运行的完整程序**：

```go
protocol.Provide{
    Action: "sleep",
    Tool:   true,
    Async:  true,
}
```

含义逐项读：动作名是 `sleep`；允许进入模型工具目录；这项动作会先回执、后补报。字段里没有 `Batchable:true`，所以不能根据“可给模型用”就推断“可被 batch 批量用”。

### 第四步：沿 actionSleep 追输入、状态、输出

假设已经建立 SUMP 服务连接，调用者给出 `ms=1000`、`note="提醒我检查结果"`。这只是业务参数示例。

1. 解码 `TimerSleepPayload`，读出时长和备注。
2. 检查时长与在计时数量限制。
3. 生成 `item_id`，保存原调用方、trace、boss 等关联信息。
4. 建立 `time.Timer`，把工作放进 pending 表。
5. 回受理结果；无需等 1 秒过去。
6. 到时回调取出那一项，发独立 `report_result`。

**回调**就是“事件发生后再执行的函数”。不是先让处理函数睡一秒，再给原请求返回。

现在你已经能找到三种“状态”：原网络请求是否返回、计时条目是否仍在 pending、最终补报是否到达调用者。三种状态关联，但不等同。

### 第五步：测试把这些约定写成可检查的条件

打开 [timer/tests/service_test.go](https://github.com/NouSart/sump/blob/6325897cc7fa696610bc25b4c89bc77d6a7c7a43/timer/tests/service_test.go)。先按名字读：

| 测试 | 想检查的具体问题 |
| --- | --- |
| `TestSleepIsAcceptedImmediately` | 原请求是否先返回受理，而非等计时完成 |
| `TestSleepReportsAtDueTime` | 到时是否产生正确补报 |
| `TestLongTimerDoesNotBlockOthers` | 长计时存在时，其他请求能否推进 |
| `TestCancelStopsDueReport` | 取消与到时回报是否按约定处理 |
| `TestGuards` | 时长、容量等非法情况是否被拒绝 |
| `TestPortalGetsSnapshots` | 门户是否收到计时列表更新 |

测试里的小型中心和调用方称为 **测试夹具**：专门搭出的可控环境。它们可稳定验证协议行为，但不等同于使用者自己的整套真实部署。

## 4. 怎样把刚才的阅读方法迁移到其他模块

| 功能 | 从哪里开始 | 顺着哪一条数据走 |
| --- | --- | --- |
| 网页发消息 | `frontend/src/server`、`frontend/src/web` | 浏览器文字 → HTTP → user_message → 页面事件 |
| 模型调用工具 | `reasoner/server/infer.go`、`board.go` | 模型工具名/参数 → 目录校验 → 派发 → 结果入黑板 |
| 记忆召回 | `memory/server/server.go`、`compose`、`longterm` | 当前问题 → 选取历史/记忆 → resume |
| 图片与文件 | `images/server`、`files/server`、各自 `store` | 数据 → 编号 → 取回/提取 → 下游消费 |
| 命令审批与执行 | `shell/server`、`approval` | 执行描述 → 审批 → 许可核验 → 进程 → 输出 |
| 批量工作 | `batch/server`、`batch/store` | 批次请求 → 条目状态 → 并发执行 → 汇总 |
| MCP 翻译 | `mcp/server` | 外部/内部参数 → 显式绑定 → 调用关联 → 结果转换 |

目录表提供阅读起点。具体文件名以本版目录为准；不是要求一次把所有文件读完。

## 5. 第一次复现：可以先不接真模型

先阅读 [Windows 环境准备](../../基础课程/00-准备Windows开发环境.md)。本版开发环境要求包括 Go 1.26+；完整开发栈另需要 Python 3.12+ 和支持当前 frontend 的 Node.js。`CONTRIBUTING.md` 对前端建议 Node 22.18 以上，当前 CI 使用 Node 24。

有三种由浅入深的练习，选择一种就可以停下：

| 方式 | 需要什么 | 会获得什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 在线读固定版本 | 浏览器 | 看懂真实字段、调用路径 | 程序已经在自己电脑运行 |
| 跑一个现有小测试 | Go 和该测试依赖 | 看到一个明确行为被检查 | 整个项目已验收 |
| 启动整套门户 | Go、Python、Node、项目依赖等 | 从网页操作现有功能 | 未配置真实模型也能完成智能任务 |

### 5.1 从图形界面打开正确目录

1. 在文件资源管理器打开解压后的项目根目录。
2. 若用 VS Code，选择“文件 → 打开文件夹”，选这层目录。
3. 左侧点开 `protocol`、`service`、`timer` 看文件。`Ctrl+F` 查找本章给出的函数名。
4. 要运行下列命令时，选择“终端 → 新建终端”。终端当前目录应是项目根目录；若打开了子目录，先回到根目录再执行。

这里使用少量命令是为了让练习可复现。平时使用 SUMP 可以主要从门户操作，不要求用终端代替所有界面。

### 5.2 练习 A：信封打包后还原

在项目根目录的终端输入：

```powershell
go test ./protocol -run '^TestEnvelopeRoundTrip$' -count=1 -v
```

**预期**：出现这个测试的 `RUN` 和 `PASS`，末尾 `ok`。这说明字段在这次编码/解码测试中保留正确。

第一次运行可能需要下载 Go 依赖。下载失败、找不到 Go、编译报错，都不属于“测试通过”。保存错误文字即可，不要为了运行练习随便改变系统安全设置。

### 5.3 练习 B：看见注册、断开、恢复

```powershell
go test ./service/tests -run '^TestRegisterReconnectBye$' -count=1 -v
```

**预期**：测试建立自己的本机测试中心，检查首次注册、断开后的重新注册，以及关闭时的告别。它使用自己的测试端口，不要求先启动整套门户。

**能证明的范围**：这一个骨架重连场景；它没有恢复崩溃程序的业务数据，也没有验证公网安全。

### 5.4 练习 C：长短计时不互相卡住

```powershell
go test ./timer/tests -run '^TestLongTimerDoesNotBlockOthers$' -count=1 -v
```

**预期**：长计时存在时，较短计时/其他请求仍能推进，测试完成并通过。这里检查的是服务调度行为，不是承诺现实中精确到某毫秒到达。

命令里的 `./` 表示从当前目录找；`-run` 按名字选测试；`-count=1` 要求重新执行、不沿用测试缓存；`-v` 展示更多测试过程。

### 5.5 想从网页观察完整系统

按固定源码的 [运行说明](https://github.com/NouSart/sump/blob/6325897cc7fa696610bc25b4c89bc77d6a7c7a43/README.md) 准备依赖，然后在项目根目录运行：

```powershell
.\scripts\run-local.ps1
```

启动器会构建程序并准备部分依赖，可能需要联网下载。它是完整开发栈入口，所需资源多于上面的单个测试。

成功后浏览器打开 `http://127.0.0.1:9501/`。先看服务名册与设置页，再进行聊天；缺少模型凭据时，不要把“页面能打开”当成“真模型已接通”。embedding 使用 fake 后端时，也不能把聊天可用当成语义召回已启用。

若脚本被系统策略阻止，停止在此并按环境情况处理；本教程不要求长期更改执行策略、关闭防火墙或开放公网端口。测试结束按启动器说明退出，避免保留不用的服务进程。

## 6. 怎么判断“真的实现了”

最有用的证据不是一张绿色截图，而是把目标行为拆成可观察的条件。

以“计时器不阻塞其他工作”为例：

| 要落实的要求 | 代码依据 | 验证关注点 |
| --- | --- | --- |
| 先返回受理 | actionSleep 创建条目后返回回执 | 原请求在到时前返回 |
| 每条计时独立 | time.Timer 与按 item 存放的记录 | 短计时不被长计时拖住 |
| 结果不串线 | 保存 caller/trace/boss/item | 各补报关联原调用 |
| 取消有真实效果 | actionCancel 停止并删除目标 | 取消之后不再冒出原到时结果 |
| 边界输入被处理 | 时长/容量检查 | 超限返回错误且不偷偷建任务 |

再区分证据等级：

- **读过源码**：知道实现在哪里，能解释分支。
- **测试定义存在**：有检查逻辑，但还未运行。
- **指定测试通过**：某提交、某环境、某范围实际执行成功。
- **服务联调通过**：真实服务进程之间完成约定消息交换。
- **实际业务验收**：用户环境、外部依赖、结果质量满足需求。

不能用后一项的名字包装前一项。也不需要因为只做文档，就把全部产品测试再跑一遍并假装这是新的功能发布。

## 7. 如何读失败而不迷路

按发生位置分开，先避免“全部都坏了”的感受。

| 现象 | 先查什么 | 例子 |
| --- | --- | --- |
| 命令不存在 | 工具是否安装、终端能否找到 | `go` 未被识别 |
| 构建失败 | 当前目录、版本、依赖 | 找不到相邻 protocol 模块 |
| 服务启动失败 | 端口、中心地址、首次注册 | 端口被占用 |
| 连接成功但返回错误 | 动作、字段、业务校验 | 未知文件编号 |
| 先受理后没有结果 | item 关联、服务是否退出、补报路径 | 计时器进程被关闭 |
| 数据到了但回答不好 | 输入完整性、截断、模型行为 | 文件只读到部分文本 |

报告问题时，最少保留：固定提交、操作步骤、预期结果、实际结果、去除秘密的错误文字。令牌、真实个人文件和秘密配置不要放入公开 issue。

## 8. 给未来修改代码的读者

若以后增加一个能力，先问它属于哪一层：

1. 已有服务的一个小动作，还是确实需要独立数据和生命周期的新服务？
2. 能复用 `protocol`/`service`，还是外部协议需要一层翻译？
3. 返回的是最终数据，还是先回受理、以后补报？
4. 需要对模型、batch、MCP 分别开放吗？分别声明，不相互推导。
5. 网络失败后，怎样知道没执行、已执行、或结果未知？
6. 哪份数据是权威来源？页面、缓存、数据库是否各有清晰职责？

这套阅读方法的目标，是让你能沿一条数据说清“谁收到了、做了什么、保存在哪、交给谁”。能说清这四件事，再看具体语言语法会容易得多。
