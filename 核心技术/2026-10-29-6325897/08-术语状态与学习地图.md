## 1. 程序是怎样组织起来的

| 词语 | 通俗解释 | 放回 SUMP 里看 |
| --- | --- | --- |
| 源码 | 人写给开发工具看的程序文字 | `.go`、`.ts`、`.py` 等文件 |
| 编译 | 将源码转换成另一种可执行形式 | Go 构建可执行程序；TS 编译成 JS |
| 运行时 | 让某类程序实际执行的环境 | frontend 服务端运行在 Node.js 中 |
| 进程 | 操作系统中正在运行的一份程序 | timer 与 memory 通常是两个进程 |
| 服务 | 能通过约定接口处理请求的运行程序 | files 接收 read、write 等动作 |
| 模块 | 按职责组织代码的单元，含义依上下文而定 | Go Module 与运行服务不是同一个概念 |
| 库 / SDK | 供别的程序调用的一组现成代码 | service 是库，MCP SDK 实现外部协议细节 |
| 依赖 | 自己需要使用的其他代码或服务 | 编译依赖 protocol，运行时可能调用 memory |
| 接口 | 双方约定怎样调用、要给什么、会回什么 | 一个动作的参数和结果约定；也可指 Go interface |
| 实现 | 真正完成约定的代码 | files 的读取函数与格式处理代码 |
| 耦合 | 两部分相互依赖的紧密程度 | 直接访问别人私有表会加深耦合 |
| 解耦 | 把依赖收敛到清晰契约 | 通过消息请求文件，减少对保存细节的依赖 |
| 生命周期 | 一件东西从创建到结束的整个过程 | 服务启动、注册、运行、退出；或一次工具工作 |
| 后端 / 前端 | 处理业务的服务端 / 用户交互界面 | frontend 目录里同时有服务端与浏览器代码 |
| 组件 | 可组合的界面或代码单元 | React 设置卡片不是一个独立 SUMP 服务 |

例子：“我换掉 files 的内部保存方式，只要保持 read 的约定，调用者不需要知道新目录怎样组织。”这解释的是解耦目标，不是保证任意改动都没有影响；字段、错误和性能边界变化仍可能影响调用方。

## 2. 网络里的词

| 词语 | 通俗解释 | 本项目中的例子 |
| --- | --- | --- |
| 客户端 Client | 主动发起某次请求的一方 | reasoner 调 files 时，reasoner 是客户端 |
| 服务端 Server | 接收并处理请求的一方 | 同一次调用中，files 是服务端 |
| 端口 | 一台机器上用于区分网络程序的窗口编号 | 默认门户监听 9501 |
| 监听 | 程序打开地址等待连接 | 服务启动 WS 接待端点 |
| 回环 / localhost | 当前这台机器自己 | `127.0.0.1` 不代表虚拟机或另一台电脑 |
| HTTP | 网络请求与响应的一套规则 | 浏览器提交聊天消息 |
| HTTPS / TLS | HTTP 的加密传输 / 提供加密与身份验证的机制 | MCP 远程入口的传输保护 |
| WebSocket / WS | 建立后支持双方发消息的连接 | 原生 SUMP 服务通信 |
| SSE | 服务端向浏览器持续发送事件的 HTTP 通道 | 门户显示新答复或进度 |
| JSON | 用文字表示对象、列表、数字等的格式 | HTTP 参数、配置文件 |
| MessagePack | 用字节表示结构化数据的编码格式 | 原生 WS 二进制消息 |
| 序列化 / 反序列化 | 把对象变成可传输数据 / 还原对象 | EncodePayload 与 DecodeRaw |
| 信封 Envelope | 所有消息共用的外壳 | id、from、to、type、payload |
| 载荷 Payload | 信封里的业务正文 | jump 的 action 和 input |
| 协议 | 数据格式加交互约定 | 不仅字段名字，还包括什么时候回执/补报 |
| API | 可供程序使用的一组接口 | frontend 的 `/api/message` |
| Schema | 参数或结果的结构规则 | MCP 输入必须有哪些字段、字段是什么类型 |
| 心跳 Heartbeat | 定期报活消息 | 中心据此判断服务是否可能离线 |
| 注册 / 发现 | 报告自己的地址能力 / 找到别人 | register 与 roster |
| 名册 Roster | 当前服务通讯录 | 服务根据名册直接连接目标 |
| 重连 | 连接断开后再建立连接 | 不等于重跑刚才的业务动作 |

同一个程序可以同时扮演客户端与服务端。MCP 接收外部请求时是 Server，访问外部工具时是 Client；不需要因此变成两个互不相关的项目。

## 3. 编号不是一张万能身份证

| 名字 | 标记什么 | 怎么避免混淆 |
| --- | --- | --- |
| `id`（信封） | 一次请求与响应的配对 | 与文件正文里的 `id` 不是同一种含义 |
| `trace` | 相关调用的追踪链 | 是关联线索，不是授权凭据 |
| `boss` | 本跳面向谁工作、交付方向 | 由具体跳转传递，不是全局管理员 |
| `conversation_id` | 一段会话 | 一段会话中可有先后多份任务 |
| `task_id` | memory 中的任务档案 | 不等于每次工具调用都新建一个任务 |
| 工具调用 `call.ID` | 模型本轮提出的某一项工具请求 | 同时调两个工具也要分别记录 |
| `item_id` | 原生服务受理的某项后台工作 | 用来配后续 report_result |
| `job_id` | MCP 导出观察等场景的作业编号 | 不是所有服务共同使用的一种任务编号 |
| `seq` | 某范围内的顺序/版本 | timer 清单 seq 与历史消息 seq 不共用含义 |
| `revision` | 名册等对象的变化版本 | 不代表 Git 提交，也不是业务完成进度 |

同名字段在不同结构里可以有不同含义。读代码时，先确认它属于哪个类型、哪个动作，再理解它的值。

## 4. 同步、异步、并发与取消

| 词语 | 通俗解释 | 容易误解的地方 |
| --- | --- | --- |
| 同步调用 | 这次调用等待约定结果再返回 | 不表示整个系统只做这一件事 |
| 异步受理 | 先给收据，后续结果另送 | 收据不是执行成功证据 |
| 回执 Acknowledgement | 确认某一步已接收或完成 | 要看确认的是哪一步 |
| 补报 report_result | 受理之后另外发来的进度或结果 | 不是最初 response 的重复副本 |
| 并发 Concurrency | 多件工作在一段时间内交错推进 | 不保证每件都在 CPU 上同时运算 |
| 并行 Parallelism | 几件工作确实同时执行 | 仍受 CPU、网络和目标服务容量影响 |
| goroutine | Go 的轻量并发执行单元 | 不等于一个独占 CPU 的系统进程 |
| Mutex，互斥锁 | 同一小段共享操作一次只让一方进入 | 用来保护数据，不是让整个系统永久串行 |
| channel，通道 | 程序内部递送值或通知的管道 | 不同于网络 WebSocket |
| Context | 工作的取消/截止时间信号载体 | 代码要响应它，不会魔法般撤销所有副作用 |
| 队列 | 暂存等待处理的工作 | 要明确是哪层队列；shell 的 queued 不是 FIFO 队列保证 |
| 容量 / 背压 | 接不动时限制或拒绝新工作 | 返回忙碌比无限接单再失联更可解释 |
| 超时 Timeout | 在约定时长内没有得到期待结果 | 对方可能已执行，不能等同从未执行 |
| 取消 Cancellation | 请求停止某段等待或工作 | 本地不等了，不保证远端停止 |
| 副作用 | 改变外部状态的行为 | 写文件、发消息、运行命令都可能有 |
| 幂等 Idempotency | 重复请求不额外产生重复业务效果 | 需要设计与验证，不是所有 HTTP/WS 调用自带 |
| 去重 Deduplication | 识别重复项并限制重复处理 | 有界缓存不是永久、全局去重 |
| 竞态 Race | 执行先后交错影响共享状态正确性 | 单次顺序测试通过不排除它 |
| 终态 Final state | 该段状态生命周期结束 | 结束可能成功、失败、取消或结果未知 |

用两句话检验理解：“我不再等快递”描述我的等待；“快递被撤回”描述配送执行。它们有关，但需要不同机制，不能互相证明。

## 5. 数据、模型与检索

| 词语 | 通俗解释 | 对应位置 |
| --- | --- | --- |
| LLM | 大型语言模型，根据输入生成文字或结构化请求 | reasoner 调用的模型接口 |
| Agent，智能体 | 能围绕目标选择并使用工具推进工作的系统 | 不能只把一个模型回复框当全部实现 |
| 推理 Inference | 用已训练模型计算本次输出 | 与重新训练模型不同 |
| Token | 模型处理文字时使用的分块单位 | 不固定等于一个汉字或一个英文词 |
| 上下文 Context | 本次模型可参考的输入材料 | 消息、工具结果、记忆；与 Go Context 要按语境区分 |
| 工具调用 Tool call | 模型提出的结构化能力请求 | 真正执行仍由程序和目标服务处理 |
| 黑板 Board | 进行中任务的临时共同记录本 | reasoner 的 messages、pending、gen 等 |
| 召回 Recall | 从保存的资料里挑本次相关材料 | memory 组装上下文 |
| 向量 Embedding | 把文字表示成一串可比较的数字 | embedding 计算，memory 使用 |
| 维度 Dimension | 向量里数字的数量 | 维度相同仍不保证来自相同语义空间 |
| 余弦相似度 | 比较向量方向接近程度的分数 | 不是“内容为真”的概率 |
| bigram | 用相邻二字等片段比较字面相似 | memory 语义不可用时的检索回退 |
| 经验线头 | 一组相关经验的简短入口 | memory 经验网按当前查询生成 |
| SQLite | 程序内部使用的文件型数据库 | 各数据服务独立管理 |
| 表 / 行 / 索引 | 一类记录 / 一条记录 / 查找或约束结构 | tasks 表，一条任务，活跃任务唯一约束 |
| 事务 Transaction | 一组数据库操作成套成功或回滚 | 不自动覆盖别的服务、网络和磁盘文件 |
| BLOB | 数据库中的二进制数据字段 | 向量或其他字节内容 |
| 持久化 | 写到程序结束后仍能保留的位置 | SQLite、文件 |
| 缓存 | 为减少重复工作保存的副本 | 丢失后应能按约定重建 |
| 元数据 Metadata | 对数据的描述 | 文件名、类型、大小 |
| 软删除 | 标记不可见而非立即物理抹除 | memory 的 deleted 状态 |
| 截断 Truncation | 超限只保留部分内容并标记 | files 文本、shell 输出 |
| Base64 | 二进制内容的一种文字编码 | 图片/文件传输；不是加密 |
| MIME | 内容类型标签 | text/plain、图片或 Office 文件类型 |

这些概念在 [数据服务一章](04-记忆向量与文件数据.md) 中放进了完整例子。先明白“谁保存原文、谁只拿编号、谁计算向量”，再记技术名词。

## 6. 权限与协议翻译

| 词语 | 通俗解释 | 本项目的边界 |
| --- | --- | --- |
| 认证 Authentication | 确认请求者凭什么被识别 | Bearer 凭据等；from 字符串本身不是认证 |
| 授权 Authorization | 决定被识别的请求者可以做什么 | 显式导出列表与归属检查 |
| Bearer Token | 持有它就可按约定访问的秘密字符串 | 不能放进公开日志或教学截图 |
| AST | 代码按语法拆出的树状结构 | 审批分析 PowerShell 命令 |
| 执行计划 Plan | 本次实际准备执行的描述 | 命令、目录、解释器、限制等 |
| 摘要 Digest | 一组字段的计算指纹 | 检查审批与执行描述一致；不等于数字签名 |
| TTL | 一项记录/许可可以存在或有效的时间 | 观察记录过期不等于命令被取消 |
| fail-closed | 不能确认允许时维持拒绝执行 | shell 审批失败不当放行 |
| Sandbox，沙箱 | 用操作系统等机制限制执行范围 | 文本规则检查不是完整沙箱 |
| MCP | 外部应用调用工具/数据的一套协议 | 本模块做双向翻译，不替代任务规划 |
| Import，导入 | 让内部调用外部能力 | 显式绑定远端工具 |
| Export，导出 | 让外部调用选定内部能力 | 与导入单独授权 |
| Stateless，无状态请求 | 不依赖某个传统会话过程维持请求关系的设计 | 不代表应用不能保存临时 job 观察记录 |
| Prompt injection，提示词注入 | 外部内容试图被当成指令影响模型行为 | 内容边界、工具权限与执行控制共同相关 |

一句话对应三种不同检查：**协议能解析吗？调用者有资格吗？实际行为获准吗？** 前一项通过，不能代替后两项。

## 7. 同一个词，在不同模块有不同意思

| 看见什么 | 应该怎样问 |
| --- | --- |
| `ok:true` | 是传输/适配请求成功，还是业务结果成功？ |
| `accepted` | 谁接受了什么：消息、计时、批次还是模型工具派发？ |
| `queued` | 是真实排队，还是历史沿用的受理阶段名？ |
| `done` | 哪一层结束？shell 仍要读 exit_code 与 timed_out |
| `final:true` | 谁结束了报告？是否仍存在远端未知副作用？ |
| `unknown` | 是未知句柄，还是不知道外部执行结果？ |
| `batch` | reasoner 的通知模式，还是独立批处理服务？ |
| `resume` | memory 回传上下文、任务切换，还是 batch 恢复派发？ |
| `context` | 模型输入材料，还是 Go 的取消/超时对象？ |

读状态时最好补全句子：“**哪个模块**认为，**哪件工作**到了**哪个阶段**，依据是**哪条消息或哪份记录**。”

## 9. 三张可以自己填写的小卡片

### 模块卡

```text
模块名：
负责的一个具体工作：
输入由谁发来，主要字段是什么：
读取/写入自己的哪份数据：
需要请求哪个服务：
输出给谁：
失败时返回什么，不能承诺什么：
源码处理函数与对应测试：
```

### 请求卡

```text
用户原话：
入口收到什么：
模型这轮知道什么：
工具真正收到什么：
现在是受理、执行、等待、终态中的哪一步：
哪些编号连接了前后两段：
最后用户看见什么，数据库留下什么：
```

### 验证卡

```text
源码提交：
希望证明的一个行为：
输入与前置条件：
预期可观察结果：
实际是否运行：
如果运行，实际输出是什么：
这项证据没有覆盖什么：
```

这三张卡帮助把“大概懂了”变成可追踪的理解。它们是个人练习格式，不是要求向项目提交额外开发过程文档。
